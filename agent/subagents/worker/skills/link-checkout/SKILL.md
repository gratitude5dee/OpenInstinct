# Link Agent Wallet checkout

Use this procedure only for the buyer-side Link Agent Wallet browser flow. Do not use Shared Payment Tokens, MPP, UCP, or a merchant-side Stripe Payment Element flow.

1. Keep one owned browser and the same worker session for the whole checkout. Create it with `manage_browsers` using `purpose: "link_checkout"` and `timeout_seconds: 1800`; the purpose also enforces that 1800-second minimum so the approval window cannot outlive the session. Before approval, fill contact and shipping fields so tax, shipping, and the final total are settled. The resulting value priority is transaction-specific values explicitly supplied by the coordinator, then Link, then the vault. Because Chromium autofill can update a whole form, enforce that priority with this sequence:
   - focus the intended contact section and call `fill_checkout_from_link` only for the needed contact `categories`;
   - focus the shipping section and call it separately for `shipping_address`;
   - for categories Link reports as missing, use a compatible opaque vault handle with `fill_from_vault` and restrict `fieldCategories` to only those missing categories;
   - re-apply every transaction-specific contact or shipping value supplied by the coordinator last, without reading any existing field value, so explicit values always win;
   - ask the coordinator for any remaining non-secret field.
2. Never inspect, read back, screenshot, log, or return a value injected by a Link or vault tool. Those tools report only safe field categories and states.
3. Re-read the merchant, item names, quantities, options, currency, and unambiguous final amount due after contact and shipping are filled. Call `request_link_spend` only with that final quote. Keep `context` free of contact details, addresses, or other personal data. The tool inspects the payment surface itself and chooses Link Pay Token only when the hidden steering checkbox and both same-frame Stripe markers are valid; otherwise it requires an ordinary card form and selects a one-time virtual card.
4. A pending spend request is the two-phase boundary. Finish with a failure result whose message begins exactly `Link approval required:` and includes the approval URL, opaque handle, route, approved quote, browser session ID, and live-view URL. Preserve the browser and stop. Link approval is the purchase authorization: after approval the coordinator resumes this exact worker and no additional chat confirmation is required.
5. On resumption re-read the current quote, then call `complete_link_payment` with the same browser and opaque spend handle. Polling is bounded. When it is still pending, preserve the browser and finish with a failure result beginning exactly `Link approval pending:` so the coordinator silently resumes this worker again. For an auto-resuming action, preserve the browser and begin the failure result exactly `Link action required (auto-resume):`, including its action URL. Denied, expired, canceled, failed, materially changed, or non-auto-resumable action states are terminal for this checkout.
6. The approved quote remains valid only for the same merchant, origin, items, quantities, options, and currency at the approved total or lower. An increase or material order change requires a new Link spend request. Never silently switch to a vault card after denial, expiry, cancellation, a changed quote, or a failed Link route.
7. `complete_link_payment` retrieves and injects the credential internally. LPT use is bound to the same origin, Stripe frame, and merchant account. It may retrieve one fresh LPT and retry injection once; if the saved-payment state still does not appear, stop. Changing an approved LPT request to a virtual-card route requires a new approval.
8. The completion tool submits at most once. Treat success as verified only when it returns an order-confirmation page or order identifier. If submission is ambiguous, never click Pay or Place order again automatically, never create a replacement spend request, and never claim that a new request is needed: the original submission might already have charged. Preserve the browser for 3-D Secure, CAPTCHA, passkey, push approval, or another human-only challenge and return the exact blocker to the coordinator.
